# AirGuard: Delhi NCR air quality forecasting

A 10-day forecast of daily AQI, PM2.5 and ozone for five Delhi monitoring stations, built from station
history, ERA5 meteorology, CAMS aerosol and FIRMS stubble-fire detections, with a walk-forward
evaluation, and live data ingestion via GitHub Actions and Postgres.

## Scope

This is a data-driven forecasting system. It is **not** a coupled weather-chemistry simulation
(WRF-Chem); the weather-pollution feedback is represented through proxies (inversion strength and
persistence, boundary-layer depth, clearness index, diurnal temperature range, met-chemistry
interaction terms), tested statistically in both directions in the notebook.

## How to run (one-time, locally)

```bash
pip install -r requirements.txt
jupyter nbconvert --to notebook --execute --inplace baseline_walkforward_CLEAN_v9.ipynb
```

`final_delhi_dataset.csv` must exist first (run `data_preprosessing.ipynb`, or see "Live data ingestion"
below). `build_features.py` runs on its own too (`python build_features.py`) and writes `features/`;
the notebook reads from there.

## Live data ingestion (GitHub Actions + Postgres)

Four sources keep the dataset current between manual rebuilds: **CPCB** (station pollutant
concentrations, via the official data.gov.in API), **NASA FIRMS** (fire detections, NRT), **Open-Meteo**
(surface and pressure-level weather, observed-recent + forecast), and **Copernicus ADS** (CAMS global
aerosol forecasts). A single Postgres database holds both the migrated historical CSVs and everything
ingested going forward; `ingestion/export_for_modeling.py` reshapes it back into the CSVs
`build_features.py` already reads, so the feature pipeline and notebook above do not change.

```
Postgres
├── historical tables (station_hourly_hist, era5_surface_hist, era5_pressure6h_hist,
│   era5_pressure12h_hist, cams_3h_hist) -- loaded once by ingestion/migrate_historical.py
├── live tables (cpcb_hourly, weather_surface_hourly, weather_pressure_hourly,
│   cams_hourly, fire_detections_raw) -- filled every 3h by .github/workflows/ingest.yml
├── ingestion_log -- one row per job run of any workflow; also how
│   .github/workflows/retrain_model.yml knows whether a retrain is overdue
├── .github/workflows/rebuild_forecast.yml, daily:
│   export_for_modeling.py -> rebuild_fire_daily.py -> build_features.py ->
│   data_quality_check.py -> predict_forecast.py (loads outputs/models/, predicts, no fitting) -> commit
└── .github/workflows/retrain_model.yml, gated to ~every 30 days:
    export + features + quality check (same as above) -> train_production_models.py
    (fits outputs/models/, fixed params/weights, no tuning) -> commit
```

### Scheduled retraining (30-day walk-forward)

The forecast and the models behind it are now updated on two different clocks:

- **Daily** (`rebuild_forecast.yml`): `predict_forecast.py` loads whatever models
  `outputs/models/` already holds and scores them against today's features. It never
  calls `.fit()`.
- **Every ~30 days** (`retrain_model.yml`): `train_production_models.py` refits the
  ensemble members on all data available as of that day and overwrites `outputs/models/`.
  It always reads `best_params_*.json` / `ensemble_weights_*.json` as-is -- the same
  tuned hyperparameters and ensemble weights are used on every retrain; only the training
  data window grows. Re-tuning those files is a separate, much rarer job
  (`research_retrain.yml`).

`retrain_model.yml` runs its gate (`ingestion/check_retrain_due.py`) daily rather than on
a fixed day-of-month cron: it queries `ingestion_log` for the last successful
`retrain_models` row and only lets the (expensive) retrain steps run once at least 30 days
have passed. That's robust to a missed/failed run -- it retrains as soon as it notices
it's overdue, rather than waiting for a calendar date it already missed. Trigger an
out-of-cycle retrain any time from the Actions tab with the `force` input.

`model_common.py` holds the data loading, feature construction and model definitions
shared by both scripts, so they can't drift apart. `build_final_models.py` is now a thin
convenience wrapper (`train_production_models.main()` then `predict_forecast.main()`) for
running both steps locally in one go -- useful right after first setup, when nothing has
been trained yet.

### One-time setup

1. **Create a Postgres database** reachable from GitHub Actions (Neon, Supabase, Railway, RDS, or your
   own server -- GitHub Actions itself has no persistent storage).
2. **Add repository secrets** (Settings -> Secrets and variables -> Actions): `DATABASE_URL`,
   `FIRMS_MAP_KEY`, `CDSAPI_URL`, `CDSAPI_KEY`, `CPCB_API_KEY` (see `ingestion/config.py` for where each
   comes from).
3. **Migrate the existing CSVs once**, locally:
   ```bash
   cd ingestion
   pip install -r requirements.txt
   export DATABASE_URL=postgresql://...
   python migrate_historical.py --yes
   ```

### What runs automatically

- **`ingest.yml`**, every 3 hours: runs the four `ingestion/fetch_*.py` scripts, upserts into Postgres.
  One source failing does not block the others (`run_all.py`).
- **`rebuild_forecast.yml`**, once daily: `export_for_modeling.py` rebuilds the source CSVs from
  Postgres, `rebuild_fire_daily.py` regenerates `fire_daily_features.csv` by calling your existing
  `fire_features.py` against historical-plus-live detections, then `build_features.py` and the notebook
  run as usual, and the results are committed back to the repo.

### Things worth checking before you trust it

- **`build_features.py`'s `PERIOD_END`** was hardcoded to `2025-12-31`; it would have silently discarded
  any live-ingested day past that. `main()` now extends it to the latest date actually present in
  `final_delhi_dataset.csv` each run (never earlier), so this needed fixing for ingestion to matter at
  all -- worth knowing in case you have other scripts that import the old constant directly.
- **CPCB's live feed lacks station weather.** The data.gov.in resource gives pollutant concentrations
  only -- not the AT/RH/WS/WD/BP/SR/TOT-RF columns your CAAQMS downloads have. Live rows backfill
  `temperature`, `humidity`, `wind_speed`, `wind_direction`, `pressure` (hPa converted to mmHg),
  `solar_radiation` and `total_rainfall` from the single Delhi-wide Open-Meteo pull, applied identically
  to all five stations -- a city-wide proxy, not each station's own sensor. `rainfall` and
  `vertical_wind_speed` have no live source and stay NaN, which doesn't matter: `build_features.py`
  drops both columns outright already.
- **FIRMS NRT MODIS has no `type` field** (0 = presumed vegetation fire), which `fire_features.load_modis()`
  filters on. The historical archive is the quality-controlled product that has it; NRT doesn't. Live
  MODIS rows are written with `type = 0` for all of them (the historical majority class) rather than
  dropped -- a disclosed approximation, not a verified fact about each detection.
- **`q` (specific humidity) and `w` (vertical velocity)** on pressure levels aren't available from
  Open-Meteo's general forecast model, so they're NaN in the live tail; `era5_pressure_levels_12h_ist.csv`
  (the 4-point grid) has no live source at all and stays historical-only. Features built only from these
  will have more missing values past the historical cutoff.
- **Four derived ERA5 columns** (`era5_inv_surface`, `era5_inv_deep`, `era5_lapse_925_700`,
  `era5_ventilation`): whatever originally computed these for the historical CSV wasn't available to
  reconstruct exactly, so `export_for_modeling.py` uses its own documented physical formulas. Expect a
  small, visible step at the historical/live boundary in exactly these four columns; everything else is
  a straight rename or unit match.
- **CPCB station names** (`config.py`) are matched against `final_delhi_dataset.csv`'s own `station`
  column (confirmed against `data_preprosessing.ipynb`'s `station_mapping`), but the exact string CPCB
  reports live (e.g. `"Anand Vihar, Delhi - DPCC"`) is unverified against the real API. `fetch_cpcb.py`
  prints the names it actually sees if one doesn't match, so this is easy to catch and fix on first run.
